# cNote 工程笔记

这份文档只讲实现：开发过程中的实测数据和取舍理由。使用与快捷键见
[release/README.md](../release/README.md)，项目概览与构建见 [README.md](../README.md)。

数字来自不同阶段的测量，有些是同一份代码在不同优化阶段的对比，我都标了当时的条件。

## 构建与打包

构建命令见 [README](../README.md#从源码构建)。构建脚本不依赖 `vcvars64.bat`：
它自己找工具链（`..\vs`、`..\sdk` 优先），把 include / lib 路径显式传给编译器。
这台机器上 vcvars 找不到 SDK，所以一开始就是这么做的。

**前端先 minify 再压缩。** `tools\gen-assets.ps1` 会用 `minify.mjs`（esbuild）把
HTML/CSS/JS 的注释、空行和多余空白去掉，变量名也会缩短，然后用 Windows 自带的
Compression API（MSZIP 就是 deflate）压进 `src/assets.generated.h`，
运行时用同一个系统 API 解码——**解压器不占 exe 体积**。

| 阶段 | 体积 |
| --- | --- |
| `assets/` 源码 | 450 KB |
| minify（去注释、去空白） | 217 KB |
| deflate 后嵌入 | 75 KB |
| 最终 exe（去注释构建） | 395 KB |
| 最终 exe（不装 esbuild、原样嵌入） | 462 KB |

不装 esbuild 也能构建，只是前端带着注释进 exe，`gen-assets.ps1` 会在日志里说明。
C++ 那份注释本来就不进二进制（预处理器在编译前去掉），生成的 `assets.generated.h`
和 `resources.rc` 也都不写注释：**注释只留在源码里**。

## 启动

日志里有分段计时（`boot: window shown / environment / controller / page ready`），
热启动实测：

```
boot: window shown 15ms
webview: statically linked loader
boot: environment 31ms
boot: controller 234ms
boot: page ready 296ms
```

窗口 15 ms 就出现，页面约 0.3 s 就绪。刚编译出来的 exe 第一次启动会被安全软件扫描，
可能到 2~3 s，之后恢复。窗口在页面渲染出来之前先用主题色铺底，所以看不到白闪；
每次打开都居中到鼠标所在显示器的工作区。

## 大文档性能

136k 行 / 1.5 MB 文档上的实测：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 单键延迟 p50 | 2004 ms | **38 ms** |
| 查找（1.2 万处命中） | 4264 ms | **6 ms** |
| 保存 1.5 MB | 8118 ms | **200 ms** |
| 打开 + 首次渲染 | 3788 ms | 1142 ms |

编辑器只画视口附近的行、按行增量重绘，预览用 `content-visibility` 跳过屏外块。

第二轮把预览和解析器一起按行/按块切开，并修掉两处平方级热点：

| 指标 | 之前 | 现在 |
| --- | --- | --- |
| 编辑后重建预览（1.95 MB） | 1212 ms | **80 ms** |
| 首次预览 1.95 MB | 1212 ms | **115 ms**（首屏 4 ms） |
| 编辑后重建预览（8.15 MB / 350k 行） | 3812 ms | **350 ms** |

`Markdown.render(text, { blocks: true })` 会连同 HTML 一起返回顶层块的切分；预览对前后缀
做 diff，只重建中间变掉的那几块；首屏之外的部分按帧补齐，窗口立刻可用。
大纲按标题指纹缓存，正文里打字不再重建几千行 DOM。
日志里超过 40 ms 的一次预览会记成 `preview: Nms parse + Nms first paint`。

### 两处平方级热点

都是"看着无害的一行"：

- `renderTable(lines.slice(i), …)` 给每个表格切片整个行数组。文档每节一张表时，
  8 MB 的解析要 5.5 s，而 2 MB 只要 0.6 s；改成传 `(lines, start)` 后两条曲线都回到线性。
- `inline()` 对每个 token 执行 `text.slice(i)` 再做 `^…` 匹配，等于把段落剩余部分复制一遍。
  改成 sticky 正则（`/…/y` 配 `lastIndex`）在原串上按位置匹配，和 `highlight.js` 用的是同一招。

解析器本身按首字符分派（markdown-it 的做法），高亮的关键字表按规则文本缓存。
构建对热路径（`json.cpp`、`util.cpp`，整篇文档每次保存都要过它们）保留 `/O2`，
其余代码用 `/O1` 换体积——实测省 27 KB，而 2 MB 的保存往返仍是 ~30 ms。

### 渲染热路径：四个明确的浪费

重新 profile 之后，最大的一块变成了 GC（35%），排在它后面的几项都能点名：

- **`fillToc` 占了 119 ms**：它要判断文档里有没有 `[TOC]`，做法是对 24 MB 的 HTML 串做
  `indexOf`。解析时本来就知道有没有发过占位符，加一个标志即可——这项归零。
- **`slugify` 对每个标题跑 7 遍正则**。改成一次字符扫描后 65 ms → 50 ms，也不再依赖正则行为。
- **高亮对每个标识符查 4 个成员集合**（literals / keywords / types / builtins），
  也就是每个词 4 次字符串哈希。合并成一张按类别标记的表后剩 2 次查找（一次小写、一次精确），
  并且用语言规则对象本身作缓存键——之前是用规则文本拼一个几百字符的 key，每块代码都要拼一次。
- **行准备对整篇文档做正则扫描**（把 CRLF 归一化）。只有在真的存在 `\r` 时才做。

这一轮整体只快了几个百分点：剩下的大头是 GC，而它来自"拼字符串建 HTML"这个根本做法。
要再往下走就得改渲染架构（流式或分块输出），那是另一个量级的改动。

## 解析器：拿 CommonMark 官方套件当验收标准

`markdown.js` 自称 CommonMark/GFM 子集，所以用 **CommonMark 0.31.2 的 652 个官方用例**跑了一遍。
测试对样式包装做了归一化（我们给代码块加了语言标签和复制按钮，规范只要裸的 `<pre><code>`），
剩下的差异都是真的。

一开始 220/652，补上三个真实缺口后到 **261/652**：

| 章节 | 之前 | 现在 |
| --- | --- | --- |
| 缩进代码块（4 空格） | 1/12 | **8/12** |
| 围栏代码块 | 3/29 | **18/29** |
| Tab | 1/11 | **5/11** |
| 列表 | 3/26 | **5/26** |

- **缩进代码块**完全没有：从别处粘一段 4 空格缩进的 Markdown 进来会被渲染成普通段落。
- **Tab 不按 4 列展开**：现在行首空白里的 Tab 展开到下一个 4 的倍数，第一个非空白字符之后的
  Tab 是内容、原样保留（`\tfoo\tbar` → 四空格 + `foo` + 字面 Tab），与规范示例一致。
  快速路径让这个改动对性能没有影响：2 MB 文档 127 ms、8 MB 526 ms，与改前持平。
- **代码块内容缺少结尾换行**：规范输出是 `<pre><code>foo\n</code></pre>`。加上之后测试夹具的
  字节数正好增加"代码块数 × 1"，说明改动精确；浏览器里确认没有多出可见空行。
- **混合列表标记**：`- foo` 后面跟 `1. bar` 原本会并进同一个 `<ul>`，现在按规范分成两个列表
  ——这是对比时顺带发现的既有 bug，夹具里每节的字节数都因此减少。

仍然不合格的是 `Emphasis`（39%）、`Links`（27%）、`HTML blocks`（52%）这些——它们本来就不在
这个子集的承诺范围内，没有为了分数去补。

## 体积：把 C 运行时的浮点部分请出去

符号表上最大的一块不是应用代码，而是 C 运行时。两处调用把它整个拉了进来：

- **`strtod`（约 20 KB）**：JSON 只用到 RFC 8259 §6 定义的数字语法——可选负号、整数、
  可选小数、可选指数，没有十六进制、没有 `inf`/`nan`、不看 locale。照着规范手写不到 40 行，
  `strtod` 就整个离开了链接。`std::from_chars` 是更"标准"的替代，但在 MSVC 上它带来 Ryu，实测反而更大。
- **`printf`（约 8 KB）**：`snprintf` 的格式串是运行时读的，所以哪怕只写 `"%lld"`，
  链接器也必须带上**完整**的格式化器，含浮点。程序里一共 7 处格式化（时间戳、颜色字节、
  HRESULT、CF_HTML 头、图片文件名），全部换成两个手写的辅助函数后，`cfout`/`cvt` 从符号表上消失。

两处替代都由单元测试对着标准实现验证：27 个合法 + 10 个非法 JSON 数字对比 `strtod`，
26 个浮点值（含 `1e-5`、`1e6`、`9.999999` 这类边界）对比 `%.6g`，全部逐字符一致。

另外两处同样来自符号表而不是猜测：

- **C++ 异常框架**（`frame` + `risctrnsctrl`）曾经占约 16 KB。整个程序没有任何
  `try`/`catch`/`throw`，所以 `/EHs-c-` 是安全的：它关掉的是一套从未被使用的展开机制。
  用 2 MB 文档跑过打开、编辑、保存全流程确认无碍。
- **locale 表**（`wcsicmp`、`mbctype`）：路径比较用的 `_wcsicmp` 和 `towlower` 每字符都查表。
  换成手写的 ASCII + Latin-1 折叠后 `wcsicmp` 从符号表消失；CJK 本来就没有大小写，
  这些表对笔记软件是纯开销。

最终符号表里最"重"的已经全是应用自己的代码和 WebView2 的 loader，C 运行时只剩 `frame`
（结构化异常，操作系统要求）、堆与 `std::string` 的基本支撑。

## 预览改成了视口渲染

一份 2 MB 的笔记曾经会变成 **21 万个元素 + 30 万个文本节点**，渲染进程占 **772 MB**。
按 CodeMirror System Guide 的 Viewport 章节重写之后：

| 指标 | 之前 | 现在 |
| --- | --- | --- |
| 预览里的元素 | 214,200 | **约 150** |
| 整个文档的节点 | 218,201 | **约 4,200** |
| 渲染进程占用 | 772 MB | **567 MB** |
| 预览 HTML 字节 | 5,851,874 | 4,231（只算画出来的） |

做法本身就在文档里：*"只渲染当前可见的部分加一个边缘范围……它会为整个文档跟踪高度信息，
初始估算、内容绘制时精确测量；视口外的坐标查询不可用，因为没渲染、没有布局。"*

具体到这套代码：

- **滚动范围由两个 spacer 撑开**，不是每块一个占位符——2 MB 笔记有 23,000 个块，
  每块一个占位就等于把虚拟化想省的那 23,000 个元素又加回来。这是 CodeMirror 里 sizer 的形状。
- **高度先估算后精测**：块第一次进窗口时按源码行数估，画完就用 `getBoundingClientRect`
  换成实测值。滚动条随着阅读越来越准。
- **锚定**：换掉 spacer 会移动它下面的所有内容，所以每次重排前先记住视口顶部落在哪个块、
  进了多少，重排后放回去。没有这一步，读者每滚一次位置就漂一点——加之前夹具的滚动位置会偏 3%，
  加之后稳定在 0.5% 以内。
- **视口外的坐标要从高度表拿**：`previewTopForEditor` / `editorTopForPreview` 原本用
  `getElementById` 找标题元素，视口一虚拟化就再也找不到，大纲跳转和分栏同步都会退化成按比例滚动。
  现在改成查块表，跳转回到准确。
- **打印和 PDF 导出前先把所有块画出来**：这两个操作让 WebView2 渲染页面而不是模型，
  只画一屏的话导出的就是那一屏。

## 分栏对齐：两个量错的地方

分栏同步不是两边同时滑，而是**谁先滑谁动，停下 90 ms 后另一边直接定位过去**。
连续同步要求预览每帧重建窗口，而窗口里任何一点误差都会在左边还在动的时候显示成右边在漂；
一次定位只走一遍，读起来也更清楚是自己在滚哪一边。

定位要准，靠的是两个修好的量：

- **`.md > *:first-child { margin-top: 0 }` 被 spacer 挡住了**：预览顶部那个撑高度的空 spacer
  成了 `#preview` 的第一个子元素，于是真正首块保留了自己的 33px 上边距，这个边距又塌陷出
  article，把整个右栏往下推了 33px——这就是"右边比左边低一截"。现在补了一条
  `.md > .md-spacer + * { margin-top: 0 }`，顺带让首块正好落在 spacer 的高度上，
  也就是高度表说它在的地方。
- **`scrollTop / lineHeight` 数的是行，不是源码行**：一个换行的段落占好几行，按行数当源码行数用
  会一路超读；欢迎文档的 `[TOC]` 是 1 行源码、右栏十几行列表，两边在它附近差了三分之一屏。
  现在窗口每次重绘时量一次每行的起始位置（一次矩形读取，之后所有滚动事件复用），
  定位时按这个表二分，并把"停在某一行的哪个位置"当成比例带过去，换行的行才真正对上。
